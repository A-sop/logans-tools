# RR-010 step 1: Watchman — Amendment 1 (build session, 1 Nov 2026)

Committed on its own, after the acceptance file (235f803) and before any code. It does not change
what the watchman must do; it fixes four points the acceptance text leaves open or makes
impossible as literally written. Dept13 checks the build against AC1–AC9 as amended here.

## A1 (AC1, AC3) Dedupe and supersede together
AC1 asks for `dedupe_key UNIQUE`, and AC3 asks that a newer item on the same key supersedes the
older one (status=superseded). A plain UNIQUE on `dedupe_key` alone would reject the newer item,
so nothing could ever be superseded. Amended:
- `agent_inbox.content_md5` is a stored generated column, `md5(subject || newline || body)`.
- The unique constraint is `UNIQUE (dedupe_key, content_md5)`. An exact resend (same key, same
  text) is dropped by `ON CONFLICT DO NOTHING`. A changed text on the same key is a new row, and
  the watchman marks every older queued row on that key `superseded` on its next tick.

## A2 (AC1, AC3) Status `suppressed` and the gate's record
- `status` takes `queued | delivered | superseded | suppressed`. `suppressed` is for bare
  acknowledgements and thanks (AC3: "dropped ... never woken for"); the row is kept for the
  metrics, never delivered.
- Two extra columns record the gate: `gate_decision` (e.g. `wake:blocking`,
  `batch;downgrade:missing_reason`, `suppress:ack`) and `gated_at`.
- One extra column, `dispatched_at`, records when the watchman POSTed the row's batch, so the
  2-hour cadence (AC4) is read from the table and survives restarts. `delivered_at` stays the
  routine's own mark (AC5).
- `to_agent` may not be `logan`: Logan's yes/no items go in `approval_queue` (logans-tools #60).

## A3 (AC3) Deterministic reading of the wake reasons
- `urgency_reason` starts with a reason code, optionally followed by `:` and free text, e.g.
  `prod_down: site returns 500`. Codes for (d): `prod_down`, `data_loss`, `security`,
  `deadline_6h` (the last one also needs `deadline_at` within the next 6 h). Codes for (a), honoured
  only when `from_agent = 'ldw'`: `logan_order`, `logan_decision`.
- (b) "an agent that is actually waiting": `blocks` must name Logan or a known agent id
  (`ldw`, `div1`–`div7`; `dept13`/`dept14` read as `div5`, the agent that wears those hats).
  The watchman cannot see inside another agent, so naming a known party is the test.
- (c) applies to any queued row whose `deadline_at` falls on today's Europe/Berlin date, whatever
  the claim. "Not already done" = still `queued` (delivered, superseded and suppressed rows are
  never woken for).
- A claim that fails its test (no reason, reason code not allowlisted, `blocks` names nobody known,
  `deadline_today` without `deadline_at`) is ignored, logged as `downgrade:<why>`, and the row is
  batched unless rule (c) applies on its facts.
- FYI = subject starting `FYI`; it is batched. Ack/thanks = a subject that is only an
  acknowledgement word (received, noted, thanks, ok, on it, standing by, got it ...) with a body of
  280 characters or less; it is suppressed.

## A4 (AC5, AC6) Delivery details
- A recipient whose POST did not get a 2xx keeps its rows queued with the batch released, and is
  retried on the next tick. A batch that was POSTed but not marked delivered within 2 h is sent
  again with the next wake or batch.
- The sender key goes in the `Authorization: Bearer <key>` header by default. Two non-secret
  options, `WATCHMAN_KEY_HEADER` and `WATCHMAN_KEY_SCHEME`, change the header if the routine panel
  asks for another form.
- The watchman never reads `body` (it selects `length(body)` only), so bodies cannot reach its logs.
- The watchman's database login is its own role, `dabos_watchman`, created by Logan in SQL (as for
  the status digest). The SQL file grants it SELECT on `agent_inbox`, UPDATE on the five gate
  columns only, INSERT on the seven sender columns (A5) and SELECT + INSERT on `role_runs`.

## A5 Dept13 review rules of 1 Nov 2026, applied to this build
- (4) Failure state is never cleared by a narrower or partial run. The watchman keeps
  `~/.local/state/dabos-watchman/state.json` with its open failures. Only a full, non-dry-run tick
  that finishes with no failure clears it; a dry run, or a tick with any failure, never does.
- (5) Every failure names its owner post, **Dept12 Production, Div4**, and is routed where it is
  read: the watchman files one `agent_inbox` row per failure kind per Berlin day to `div4`
  (`from_agent = 'watchman'`, ids and counts only), exits non-zero so the unit shows failed in the
  ln02 status digest (logans-tools #61), and writes it to the journal. For this the role also gets
  column-level INSERT on the seven sender columns of `agent_inbox` (never UPDATE of them).
- (6) The grant guards check the role's whole footprint, not only the target tables: no role
  memberships at all, no owned objects, no database-level grants, exactly USAGE on schema
  `public`, and exactly the intended table and column privileges across every relation.
- (1)–(3) The watchman makes no verdict or approval decisions. It wakes for an LDW relay of a
  Logan order or decision; it never treats a relay as an approval to act.
